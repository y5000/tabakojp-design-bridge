# TabakoJP 公开设计协作中心

协作规范 v1.1.0。协调员已建立，本仓库是 GitHub 双向协作入口。首先读取 [CURRENT_TASK.md](CURRENT_TASK.md)，只有它指向状态 ready 的正式设计任务时才开始设计。本次仅接入规范，无商城设计任务。

## 分工与交付
- 用户：确认业务规则与最终验收，不承担技术文件中转。
- 协调员：通过 GitHub 发布已获授权且可公开的任务、资料、反馈；检查原型后向前端发布实施任务；统一安排后端接口依赖。
- 美工 lle2066：通过自己的 ChatGPT 读取入口，拥有新主题视觉、布局、交互设计自主权；直接向仓库提交 HTML/CSS/JavaScript 原型、必要素材与说明。业务规则或真实接口需求不擅自定案，交协调员安排。
- 前端/后端：通过私有工作列表执行实施；不得把设计提交直接当作已部署商城。

美工交付的是实际可运行原型，原则上包括移动端适配、可操作交互、素材、入口页面、运行说明、测试结果与已知限制。仅效果图不能替代。模拟数据/模拟交互必须明示，原型不使用真实用户、令牌或私有接口。

## 路径归属与冲突防护
协调员独占 README、CURRENT_TASK、tasks/、feedback/ 和 deliveries/README.md、deliveries/TEMPLATE.md、deliveries/FEATURE_REQUESTS_TEMPLATE.md。美工只维护 deliveries/<任务号>/<交付版本>/ 下自己的文件；不改任务状态、反馈或其他美工版本。tests/中已有连接测试保留；新增测试按各自前缀独立文件，不覆盖对方。归属是合作规则，不是逐目录GitHub安全权限隔离。

开始写入前读取最新main及涉及文件；提交只包含本人允许路径。多人修改优先各自分支/PR；直接提交main时采用最新父提交及非强制更新，遇并发冲突停止并重新核对，禁止强推覆盖他人。发现错误用新提交纠正，不删除历史。

## 固定命令与流程
美工收到“检查并执行设计工作列表。”，先读取CURRENT_TASK；无ready任务立即返回，不猜需求、不启动设计。读取成功后在自己的ChatGPT回复任务号、任务版本和读取的任务Commit SHA。有任务才读对应资料。需要澄清时在自己的交付目录提交QUESTIONS.md，协调员在feedback回复，用户无需中转。

任务ready → designing → submitted → awaiting_user_acceptance → accepted，另有blocked/rework/cancelled；只有协调员修改任务正式状态，accepted必须有真实用户确认。美工在交付清单记录执行状态，提交不等于验收。协调员按完整交付Commit审查，在feedback记录结果，明确reviewed/accepted依赖后才发布前后端实施任务。

GitHub不会自动唤醒其他ChatGPT；用户分别触发固定命令即可。协调员读取结果后统一处理，不需要用户转述技术内容。

## 版本及素材
任务修订创建tasks/<任务号>/vX.Y.Z.md，不覆盖已被读取的旧版本；入口指向最新版。交付创建独立版本目录，写明任务版本、实际读取的任务Commit SHA、依赖、运行方式、测试和文件SHA256。交付自己的最终Commit SHA由协调员从Git核验并写feedback，避免在同一提交中自引用不存在的SHA。详见三个目录说明。

文本写入已由lle2066验证；协调员另有PNG/ZIP诊断测试，不等于美工连接器能上传所有格式。若美工端有GitHub create_blob(base64)能力，可直接提交二进制；否则可将合法素材编码为base64文本，提交到自己的交付目录并附mime/目标文件名/大小/SHA256，协调员在隔离目录验证后还原。SVG可直接文本提交；图片也可使用内嵌data URI。ZIP不是交付必需，优先源码目录。不得要求用户手动转交文件。

外部素材只使用有许可且可公开的内容并记录来源；不依赖会过期或需要私有登录的链接。base64不是加密，禁止用它上传秘密。禁止私钥、密码、Cookie、token、客户数据、私有队列/事件/进度、服务器路径及未授权商城源码；私有协作记录不自动同步此仓库。

## 美工功能建议与前后端协作（长期规则 v1.1.0）

美工除自主视觉、布局、交互设计外，可以主动提出页面交互、数据展示、购物车、会员中心、筛选、优惠展示等新增/调整功能。建议不是业务开发授权；在交付目录提交FEATURE_REQUESTS.md，按模板逐项写功能编号、目标/新增或调整、所需数据、预期用户行为和效果、模拟与真实实现区别、接口假设及待确认业务规则。不能把未开发服务端能力写成已实现；原型中的报价、库存、支付、权限等演示必须标注模拟，真实实现服从服务端校验。

协调员先核查当前OpenCart核心、已部署插件、既有契约与近期交付证据；每项记录已有可复用/需调整/需新增/尚不确定及证据，不能把未知当作不存在或重复开发已具备接口。必要时先发布后端只读能力确认，而非直接开发。已有能力仍须核实版本、权限和适用范围，不把历史声称当现态测试。

纯前端且在既有授权范围内的工作，协调员发布私有frontend实施任务。涉及服务端接口、数据库、订单、支付、库存、会员及权限逻辑，由协调员向backend工作列表发布能力确认或获批准的开发任务；美工和前端不自行实现服务端规则。新增业务规则、支付行为、数据权限或明显扩大开发范围，协调员先向用户说明具体范围和影响并取得批准，再发布开发任务；可以在批准前做只读确认，不能将建议或本规则当默认业务批准。

backend使用私有queue.py独立提交接口说明、当前版本/Commit或无修改原因、测试证据/未测试项、结果与风险，声明existing/reuse/adjust/new及可用范围。协调员review pass后，才满足对应frontend依赖gate=reviewed；业务敏感项或任务明确要求最终验收则gate=accepted，不以技术review替代用户授权。依赖需在任务中预先声明，工具在上游正式检查满足后自动识别就绪；协调员核实后通知前端，额外blocked原因仍须按正式unblock流程处理，不暗改执行中任务定义或直接恢复旧任务。

前端领取就绪任务后按真实接口接入，仍需自身文件租约、备份及测试。用户只进行业务确认和最终验收，不在美工/前后端之间转述技术细节。公开feedback仅含可公开接口摘要；私有真实接口、授权来源、token和证据留私有区。没有新增功能建议的ready任务时，不启动业务开发。
